## 0. 结论摘要（给主 agent 的两行版）

1. **A1 的"鱼泡眼"是一个口径错**：原版 `default_fov = 90` 是**水平** FOV，我方把这 90 直接喂给了 Unity 的
   `Camera.fieldOfView`（**垂直**）⇒ 16:9 下我方水平视场 = **121.26°**（原版 90°），差 **+31.26°**。
   换算后 Unity 该填 **58.72°**。**A2 的"胳膊长"与 A1 同源**（viewmodel 由同一台相机、同一 FOV 渲染）。
2. **B1 的"平台地面材质不对"已定位到具体一组**：原版 A 点上行面里面积第 3 的 `SandCCrete`
   （A 点区域内 238,816 u² / 19 面；全图上行面第 2 名 2,549,048 u² / 198 面）被我方**回落成了 `box.png`（木箱贴图）**
   —— 出处 `BSPBUILD:52`。同一份映射表里 `SandRoad`/`SandTrim` → `path.png`、`-0Sand` → `ground.png`，也不是原版像素。
3. **C1 的"天空盒接缝"根因 = "把 Unity 的槽位方向记反了" + "up/dn 面没转"**（⛔ **agent-24 更正**；不是缺面、不是分辨率）：
   6 面像素与我方**逐像素相同（6/6，maxdiff=0）**；由原版像素导出的**真环序**确为 `ft→lf→bk→rt`
   （两两竖边逐像素差 3828 / 4777 / 4134 / 3158；镜像装配 4 条缝全对不上、总差 7×）。

   而 Unity 内置着色器里**逐字写的是 `_LeftTex "Left [+X]"` / `_RightTex "Right [-X]"`**。
   **agent-24 已改正为同名直塞**（`_LeftTex ← sky_lf` / `_RightTex ← sky_rt`；edit-mode 渲染实测接缝连续），

## 3. 推导与算式（供下一片直接抄进代码/注释）

### 3.1 A1 → A2 的关联推导（为什么改 FOV 会同时改观感）

设屏幕纵横比 `A = W/H`。原版：`fov_x = 90°`（固定）⇒ `tan(fov_x/2) = 1`。

| | 原版（水平固定 90°） | 我方（垂直固定 90°） |
|---|---|---|
| 16:9 下的 `fov_y`（Unity 该填的值） | `2·atan((1/A)·tan45°) = 2·atan(9/16) = **58.72°**` | **90.00°** |
| 16:9 下的 `fov_x`（等效水平） | **90.00°** | `2·atan(A·tan45°) = 2·atan(16/9) = **121.26°**` |
| 同一相机空间 z 处物体的**线性**屏幕尺寸 | 基准 1.0 | `tan(29.36°)/tan(45°) = **0.5625**` ⇒ 我方把 viewmodel 画成 **1/0.5625 = 1.7778 倍小** |

⇒ **方向性结论**：我方 FOV 更宽 ⇒ viewmodel 在屏幕上更**小**（不是更大）。因此
"胳膊长"**不能**只用 FOV 解释：更可能是**原版把 viewmodel 放大到 1.78 倍、导致手臂大部分被屏幕边缘裁掉**，
而我方全臂都落在画面内 ⇒ 读起来"更长"。**这条是假设，必须靠一张原版第一人称图定案**（[待定]，见 §2.2）。

### 3.2 FOV 换算（A1 的公式，写成可用代码形状）

```
// GoldSrc: fov_x 是水平、fov_y 由视口宽高算出（出处 HLSDK/cl_dll/view.cpp:1737-1747）
fov_y = 2 * atan( (H / W) * tan(fov_x / 2) )            // 度数
// Unity: Camera.fieldOfView 是垂直 ⇒ 保持"水平固定"要每帧按 aspect 反算
camera.fieldOfView = 2 * atan( tan(fov_x / 2) / (Screen.width / (float)Screen.height) )
// 16:9 → 58.72 ; 4:3 → 73.74 ; 5:4(1280x1024) → 77.32 ; 21:9(2.3333) → 46.28
```
